## 源代码控制理论 Source Control Theory

我们写代码做项目的时候，总会遇到以下问题：

- 在你的项目里搞大动作的时候，如果你后悔了，希望你之前备份过原来的代码。假设你备份了，于是你删除现在的代码，解压原来的代码的压缩包。如果你只是在尝试一些事情，那么你就不得不花许多时间处理这些**回滚**操作（**roll back**）。
- 你在与你的开发小组协作开发，你的工作的开发 A 文件的 a 代码，同事甲的工作是开发 A 文件的 b 代码，同事乙的工作是开发 A 文件的 c 代码——虽然你们开发的都不是同一块代码，但是同一份文件，你们没法多线程工作，只能单线程工作——你们需要**合并**更改（**merge**）。
- 同事甲把 X 的值从 4.5 改成了 5，但是没人知道——你需要知道：谁，在什么时候，因为什么，把哪些代码改了，从什么改成什么了，这样出了 bug 你才知道该**追溯**到哪个同事（**blame**）。
- 你更新了代码到版本 2，一些客户跟进了版本 2，然而一些客户还在使用版本 1，并且他们的设备太落后，用不了版本 2，现在他们遇到了 bug 并上报给你，于是你必须修复版本 1 的 bug，并发布版本 1.1，但同时版本 2 也在更新——你需要管理每个**历史**版本（**history**）。

为此，先后出现了两种**源代码控制理论**：集中式版本控制和分布式版本控制。

### 集中式版本控制 Centralized Version Control

集中式版本控制是有一个中央服务器负责管理所有代码，同事甲把文件 1 **签出**（**check out**）了，这个文件就被锁定了，其他人不能签出，直到同事甲把文件 1 **签入**（**check in**），这个过程叫做一次**更改**（**change**），产生文件 1 的 1.1 版本；现在同事乙终于能签出文件 1 了，他也做了一些改动，然后签入到中央服务器，产生文件 1 的 1.2 版本。

集中式版本控制的好处：

中央服务器保存了文件 1 的所有版本，这意味它可以随时回滚文件 1 到任何一个历史版本。回滚意味着我们可以做一些试错工作，假设版本 1.2 不好，容易引入 bug，那么就可以回滚到版本 1.1。

集中式版本控制的坏处：

- 集中式版本控制不允许多个人员同时更改同一个文件，自然也就没有合并更改的问题，但这本身也是一个问题。假设同事甲正在开发文件 1 的一个**功能**（**feature**），同事乙如果要修复文件 1 的一个**漏洞**（**bug**），就必须等同事甲把他的功能开发完，反过来也是一样。
- 如果中央服务器宕机了，那么所有人都无法继续工作。
- 离线工作是非常困难的，同事甲签出一些文件说：我要在飞机上检查一些这些文件，那么直到同事甲下了飞机把这些文件签入为止，其他人都不能访问这些文件。

### 分布式版本控制 Distributed Version Control

[分布式版本控制](https://zh.wikipedia.org/wiki/%E5%88%86%E6%95%A3%E5%BC%8F%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6)是约定一个或多个服务器托管所有源代码和它们的所有版本，同事甲说：我要修改文件 1，那么他会**克隆**（**clone**）整个源代码**仓库**（**repository**），包括每个文件的每个版本；同事乙要是想改个什么东西，他也会克隆整个仓库；这样每个同事的设备上都有一份源代码仓库的完整本地副本。

分布式版本控制的好处：

- 分布式版本控制只会保存每次更改中实际发生变动的内容。假设文件 1 的 1.0 版本有 1 MiB，当它迭代到 1.2 版本时，它所有版本的总大小不会是 3 MiB，而是 1 MiB 的原始内容 + 0.01 MiB 的变动内容。
- 同事甲对文件 1 做了一些修改，发现不好，可以直接就地回滚，而不需要去服务器获取文件 1 的原始版本。
- 分布式版本控制会保存谁在什么时候对哪些代码做了怎样的修改。同事甲想知道文件 1 的 1.1 版本是谁签入的，他可以就地知道。
- 同事甲签入了 1.2 版本，但此时同事乙还在 1.1 版本上修改，当同事乙把他的 1.2 版本签入时，服务器说不行，这个文件已经有 1.2 版本了，同事乙需要拉取这个 1.2 版本，合并到自己的 1.2 版本中（如果有冲突，也就是甲乙两人改了同一个地方，那么需要跟同事甲商量一下保留谁的版本），并作为 1.3 版本签入。
- 分布式版本控制是默认离线工作的，只在签入签出时才与服务器通信。同事甲在飞机上做了一些本地更改，同时其他人也可以做一些本地更改并**推送**（**push**）给服务器，同事甲下了飞机可以先把其他人推送的更改**拉取**（**pull**）并合并到自己的本地仓库，然后再推送他的更改，这样同事甲的本地仓库和服务器仓库总是可以保持最新。

## Git 和 GitHub

[Git](https://git-scm.com) 是分布式版本控制的最流行的实现。[GitHub](https://github.com) 提供服务器，从而让你和你的同事可以使用 Git 远程协作开发。你可以在本地离线使用 Git 管理你的项目版本，但如果你想跟同事协作开发的话，你应该弄一台服务器作为协作枢纽，而 GitHub 是一个主流选择。
