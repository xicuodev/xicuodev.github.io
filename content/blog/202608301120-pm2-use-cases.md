基于Node.js的“PM2”是一个守护进程管理器，可以管理应用进程并使其保持7×24小时在线。

## 1. 快速入门

1. 注册并启动应用进程：
	
	```sh
	pm2 start app.js --name "app_name" --watch
	```
	- `--name`用于给应用进程命名。
	- `--watch`用于监视当前目录或子目录的文件变更，并在发生变更时重启应用进程。注意：如果应用程序是使用`--watch`选项启动的，则停止应用程序并不会阻止它在文件变更时重启。要完全禁用监视功能，请执行`pm2 stop app --watch`或执行`pm2 restart app --watch`在应用程序重启时切换监视选项开关。
	
	或者运行非Node.js程序：
	
	```sh
	pm2 start nginx
	```
	
	```sh
	pm2 start "java -jar app.jar"
	```
	
2. 保存当前应用进程列表：
	
	```sh
	pm2 save
	```
	
3. 让当前应用进程列表开机自启动：
	
	```sh
	pm2 startup
	```
	
	这会检测当前系统的初始化系统（`systemd`、`lanuchd`等），并生成对应的开机启动脚本。复制并执行它输出的那条`sudo`命令（`To setup the Startup Script, copy/paste the following command: ...`），只需执行一次，这会对今后所有通过`pm2 save`保存的应用程序列表永久生效。

## 2. 日常维护

- 停止任务：`$ pm2 stop <id|name|...>`
- 移除任务：`$ pm2 delete <id|name|...>`
- 新增或删除任务后，再执行一次 `$ pm2 save`
- 查看列表：`$ pm2 list`
- 重启任务：`$ pm2 restart <task-name> --update-env`
- 移除初始化脚本: `$ pm2 unstartup launchd`

## 3. Windows安装PM2

```sh
npm install -g pm2-windows-startup
pm2-startup install
pm2 save
```

## 4. 解决PM2重启DSH时3080端口被占用问题

用pm2托管dsh web（[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)）之后，`pm2 restart dsh`经常重启不了，日志里都是3080端口被占用：

```
Error: listen EADDRINUSE: address already in use 127.0.0.1:3080
```

pm2托管的应用进程怎么可能出现这种问题，必须严查3080的端口占用：

```
$ lsof -nP -iTCP:3080 -sTCP:LISTEN
COMMAND     PID USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
node      81011  ror   14u  IPv4 0x81392fdcfeda9da9      0t0  TCP localhost:stm_pproc (LISTEN)
```

原来，现在3080端口上的dsh进程早已脱离了pm2的托管。`stm_pproc`是macOS给3080起的名；81011不在pm2的进程树里，`pm2 list`列不出它。`pm2 restart`只杀自己fork出来的进程，现在pm2手里没有dsh进程的pid，所以怎么重启都碰不到它。

源头在dshmarket，也就是DSH的插件市场。安装、更新插件这类操作可能会让它会引导你点它的一键重启，结果当时重启走的是`restart.js`的`scheduleRestart()`：

```js
const helper = spawn(nodeExecutable(), ['-e', restartHelperSource(...)], {
    detached: true, stdio: 'ignore', env: process.env,
});
helper.unref();
setTimeout(() => process.kill(process.pid, 'SIGTERM'), 500);
```

`helper`等端口释放，再`spawn()`生成一个全新的dsh web，命令行参数从`process.argv`原样复制，500ms后给原来的进程发`SIGTERM`终止信号，让它自我了断。新进程的父级是`helper`，`helper`一退就归`launchd`，早就不归pm2管了。

决定走不走这条路的是`restartAllowed()`，它只认`systemd`，不认`pm2`和`launchd`，因此它认为当前系统的dsh进程没有`supervisor`（“监管者”）：

```js
if (config.allowRestart !== undefined) return config.allowRestart;
return detectedSupervisor(env, ppid) === null;
```

pm2的日志里能清楚地区分dsh进程是市场退的还是pm2退的。

市场退时的两行：

```
2026-09-24T04:32:00: App [dsh:3] exited with code [0] via signal [SIGINT]
2026-09-24T04:32:03: App [dsh:3] exited with code [1] via signal [SIGINT]
```

pm2退时的三行：

```
2026-09-24T11:00:39: PM2 log: Stopping app:dsh id:3
2026-09-24T11:00:39: PM2 log: pid=53745 msg=failed to kill - retrying in 100ms
2026-09-24T11:00:40: PM2 log: App [dsh:3] exited with code [130] via signal [SIGINT]
```

市场退时的第一行前面没有pm2的`Stopping app:dsh`，且退出码不一样，DSH的启动器为两个信号提供了不同的退出码：市场发的`SIGTERM`返回`0`，pm2发的`SIGINT`返回`130`。

解决方案呼之欲出：关掉市场的重启，以后都通过pm2重启。

在`~/.dsh/profiles/web/cordis.patch.yml`加两行：

```yaml
- id: dsh-market
  config:
    allowRestart: false
```

然后通过pm2重启dsh web来让改动生效。

```sh
pm2 stop dsh
lsof -nP -iTCP:3080 -sTCP:LISTEN
kill <pid>
pm2 start dsh
```
